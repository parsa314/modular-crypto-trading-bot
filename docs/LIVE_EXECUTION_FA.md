# راهنمای اجرای زنده مستقل

`research_bot.live_runtime` مسیر اجرای پیوسته برای یک مدل ثابت PPO است. آداپتور برای **یک جفت‌ارز Spot، موقعیت خرید بدون اهرم و فروش برای کاهش یا خروج** در CoinEx، Binance یا OKX ساخته شده است. Futures، فروش استقراضی و پرتفوی چند دارایی در این مسیر پشتیبانی نمی‌شوند.

تغییر در شاخه `feature/live-ensemble-20261004` قرار دارد؛ تا پیش از ادغام، برای استفاده از این راهنما همان شاخه را checkout کنید. [گزارش آزمون‌ها و محدودیت اتصال](LIVE_EXECUTION_VALIDATION.md) همراه تغییر ثبت شده است.

درخواست مالک در ۲۰۲۶-۱۰-۰۴ مجوز افزودن قابلیت LIVE به کد بود. این تغییر هیچ معامله واقعی انجام نداده و هیچ سرویس یا استقرار خودکاری را شروع نکرده است. سرویس پژوهشی موجود همچنان `RESEARCH_ONLY / PAPER_OFF / LIVE_OFF` است؛ `LIVE_EXECUTION=true` را برای آن تنظیم نکنید. این CLI مستقل، ارتقای علمی مدل یا اثبات سودآوری محسوب نمی‌شود و آزمایش‌ها و holdoutهای قبلی را تغییر نمی‌دهد.

## آماده‌سازی مدل

از ریشه مخزن، با Python 3.11:

```bash
python -m pip install -e '.[dev,rl]'
python -m research_bot.live_runtime --help
```

مدل LIVE باید با OHLCV واقعی همان صرافی، جفت‌ارز و تایم‌فریم آموزش دیده باشد. نمونه فرمان زیر برای داده توسعه مجاز است؛ نام فایل و منشأ را با داده واقعی خود جایگزین کنید:

```bash
python -m research_bot.ensemble_rl \
  --csv /path/to/coinex_btc_usdt_4h.csv \
  --data-source 'CoinEx BTC/USDT spot 4h; public closed bars; development dataset' \
  --market-exchange coinex --market-symbol BTC/USDT --market-timeframe 4h \
  --initial-train-bars 600 --test-bars 200 --folds 3 \
  --timesteps 50000 --seeds 42,43,44 \
  --output artifacts/ensemble-development
```

قرارداد CSV و محدودیت‌های ارزیابی در [راهنمای پژوهشی مدل](ENSEMBLE_RL_CHALLENGER_FA.md) آمده است. `timestamp` شروع کندل به‌وقت UTC است و فقط کندل بسته‌شده مجاز است. فراداده `market_identity` باید با تنظیمات LIVE دقیقاً برابر باشد؛ این برچسب جای راستی‌آزمایی منشأ داده را نمی‌گیرد. خروجی مصنوعی در LIVE رد می‌شود. مدل و scaler باید از همان fold و اجرای تکمیل‌شده باشند و هش هر دو با `manifest.json` تطبیق داشته باشد. تغییر فایل‌ها یا برچسب‌زدن داده مصنوعی به‌عنوان واقعی راه آماده‌سازی مدل نیست.

fold و seed را با پروتکل ازپیش‌تعیین‌شده انتخاب کنید؛ نتیجه test مبنای انتخاب و تنظیم مجدد نباشد. وزن موقعیت و حد افت در تنظیمات اجرا نمی‌توانند از سقف‌های مدل آموزش‌دیده بیشتر باشند. هش کد استخراج ویژگی، محیط، عامل و خط آموزش نیز باید با کد فعلی برابر باشد. کنترل تاریخی CVaR از تنظیمات ثابت مدل استفاده می‌کند و حتی خارج از مهلت ورود مدل تازه می‌شود.

در شروع، اجرا ۲۹۹ کندل بسته‌شده منظم دریافت می‌کند؛ برای پیش‌فرض ۳۰ کندل مشاهده، حداقل ۷۷ کندل warmup به‌علاوه پنجره مشاهده لازم است. پس از شروع، تاریخچه کامل در journal افزوده می‌شود تا EMA و ساختارهای تأییدشده با هر پنجره جدید از نو مقداردهی نشوند. وقفه، بازنگری کندل قبلی یا ناسازگاری زمان باعث توقف می‌شود. تاریخچه اولیه LIVE ممکن است با تاریخچه طولانی آموزش متفاوت باشد؛ اثر این تفاوت روی ویژگی‌ها و تصمیم‌ها باید بررسی شود. آموزش اجرای فرضی در open بعدی دارد، اما LIVE پس از بسته‌شدن کندل با قیمت دفتر سفارش و سفارش IOC اجرا می‌شود؛ نتایج بک‌تست را عملکرد واقعی این اجرا فرض نکنید.

## تنظیمات حساب و ریسک

این نسخه پنجره مشاهده حداکثر ۲۲۲ و پنجره CVaR حداکثر ۲۹۸ کندل را می‌پذیرد تا تاریخچه اولیه کافی باشد. مسیر `kill_file` هنگام خواندن تنظیمات به مسیر مطلق تبدیل و در هویت journal ثبت می‌شود؛ راه‌اندازی از پوشه دیگری نباید مسیر توقف را عوض کند.

حساب یا زیرحساب اختصاصی باید در اولین شروع هیچ دارایی پایه و سفارش بازی نداشته باشد و فقط موجودی دارایی مظنه، حداکثر تا سقف سرمایه، داشته باشد. موجودی مثبت سایر دارایی‌ها برای حسابداری کارمزد پشتیبانی نمی‌شود. در این حساب دستی معامله نکنید و هنگام اجرای ربات واریز یا برداشت نکنید؛ تغییر موجودی توضیح‌داده‌نشده اجرا را متوقف می‌کند.

فایل JSON زیر **صرفاً نمونه است؛ سرمایه و حدود ریسک مالک هنوز تعیین نشده‌اند**. `capital_limit_quote` و `max_order_quote` بر حسب دارایی مظنه هستند؛ در این مثال USDT. زیان، افت و وزن موقعیت کسر اعشاری‌اند؛ ۰٫۰۲ یعنی ۲٪. یک basis point یا bps برابر ۰٫۰۱٪ است.

```json
{
  "exchange_id": "coinex",
  "symbol": "BTC/USDT",
  "timeframe": "4h",
  "capital_limit_quote": 100,
  "max_order_quote": 20,
  "max_daily_loss": 0.02,
  "max_drawdown": 0.08,
  "max_position_weight": 0.20,
  "max_fee_bps": 20,
  "max_slippage_bps": 10,
  "max_spread_bps": 25,
  "quote_max_age_seconds": 10,
  "entry_grace_seconds": 30,
  "poll_seconds": 10,
  "kill_file": "/path/to/private/LIVE_STOP"
}
```

حد سرمایه اولیه و سهم دارایی پایه محدود می‌شوند؛ ربات پس از زیان سرمایه مجازی تازه به حساب اضافه نمی‌کند. سقف هر سفارش ممکن است رسیدن به وزن هدف یا خروج کامل را محدود کند. حداقل مقدار/ارزش سفارش صرافی نیز می‌تواند مانع معامله شود یا مقداری خرد باقی بگذارد. spread، تازگی قیمت و دقت مقدار و قیمت پیش از ارسال بررسی می‌شوند؛ اندازه سفارش با سقف فرض‌شده کارمزد محاسبه و کارمزد واقعی پس از دریافت نتیجه تطبیق داده می‌شود. عبور از سقف وزن، ارزش دارایی پایه یا CVaR می‌تواند بین کندل‌ها فروش برای کاهش ریسک ایجاد کند؛ این مسیر خرید ایجاد نمی‌کند و رفتاری فراتر از اجرای فرضی بک‌تست است. حد زیان، افت و وزن تضمین قیمت یا زمان خروج نیستند؛ جهش قیمت و قطعی اتصال ممکن است باعث عبور از حدود شوند.

## حالت‌های اجرا

پیش‌فرض `dry-run` فقط داده عمومی می‌خواند و سفارش پیشنهادی را چاپ می‌کند. به API خصوصی دسترسی ندارد، موجودی واقعی را نمی‌خواند و سفارش نمی‌فرستد. برای پیش‌نمایش از حساب مجازی خالی با موجودی مظنه برابر سقف سرمایه استفاده می‌کند؛ شبیه‌سازی پرشدن سفارش یا paper trading نیست.

```bash
python -m research_bot.live_runtime \
  --config /path/to/private/live-config.json \
  --run-dir artifacts/ensemble-development --fold 0 --seed 42 \
  --journal /path/to/private/preview.sqlite \
  --mode dry-run --once
```

`--once` فقط یک چرخه اجرا می‌کند. بدون آن، چرخه‌ها با فاصله `poll_seconds` ادامه دارند. تصمیم مدل برای هر کندل بسته‌شده یک بار مصرف می‌شود؛ شروع خارج از `entry_grace_seconds` سفارش ورود ایجاد نمی‌کند. تنظیم فاصله و مهلت باید کوتاه‌تر از تایم‌فریم باشد.

`testnet` درخواست‌های خصوصی را به sandbox صرافی می‌فرستد و به کلیدهای همان محیط نیاز دارد. CoinEx Spot در این آداپتور sandbox ندارد و این حالت برای آن رد می‌شود. برای Binance یا OKX هم فعال‌بودن و پشتیبانی حساب، نماد و endpointهای sandbox باید بررسی شود؛ صرف انتخاب این حالت کافی نیست.

برای حالت‌های خصوصی، کلیدها را فقط در محیط محلی فرایند قرار دهید:

- `BOT_EXCHANGE_API_KEY`
- `BOT_EXCHANGE_API_SECRET`
- `BOT_EXCHANGE_API_PASSWORD` برای passphrase حساب OKX

کلید باید مجوز معامله و **بدون مجوز برداشت** باشد؛ در صورت پشتیبانی صرافی، محدودیت IP تنظیم کنید. کلیدها را در چت، فایل JSON، journal، Git یا خروجی عمومی قرار ندهید. کلیدهای testnet و حساب واقعی را مخلوط نکنید.

فرمان LIVE عمداً حالت را صریح تعیین می‌کند و به journal اختصاصی حساب واقعی نیاز دارد:

```bash
python -m research_bot.live_runtime \
  --config /path/to/private/live-config.json \
  --run-dir artifacts/ensemble-development --fold 0 --seed 42 \
  --journal /path/to/private/live-account.sqlite \
  --mode live
```

این فرمان، پس از آماده‌بودن حساب، مدل و تنظیمات، **می‌تواند سفارش واقعی ارسال کند**. نمونه بالا فرمان شروع توسط اپراتور است و در تهیه این تغییر اجرا نشده است. موفقیت آزمون‌های نرم‌افزار یا پیش‌نمایش، صلاحیت اقتصادی مدل را ثابت نمی‌کند.

## سفارش، بازیابی و توقف

سفارش از نوع limit با `IOC` است: مقدار قابل اجرا فوراً پر می‌شود و باقی‌مانده لغو می‌شود. قیمت محدود است، اما پرشدن کامل تضمین نمی‌شود. قصد سفارش و شناسه یکتای آن پیش از درخواست شبکه در SQLite ثبت می‌شوند. اگر صرافی سفارش را پذیرفته باشد ولی پاسخ یا فرایند قطع شود، راه‌اندازی بعدی همان سفارش را بازیابی می‌کند؛ سفارش با وضعیت نامعلوم دوباره ارسال نمی‌شود. تا تطبیق سفارش و موجودی، سفارش جدید مسدود می‌ماند.

کارمزد گزارش‌شده باید با تغییر موجودی تطبیق کند. اگر ارز/مقدار کارمزد هنوز گزارش نشده باشد، فقط بازه محدود تا `max_fee_bps` پذیرفته می‌شود؛ اختلاف بیش از آن باعث مسدودشدن می‌شود. شناسه سفارش، موجودی و وضعیت صرافی را بررسی کنید و برای رفع ابهام journal را حذف نکنید.

journal هویت حساب، حالت اجرا، مدل و تمام تنظیمات را به راه‌اندازی بعدی مقید می‌کند؛ با همان فایل و همان تنظیمات ادامه دهید. فایل پیش‌نمایش را برای LIVE استفاده نکنید. برای همان حساب فعال، ساخت journal تازه راه تغییر تنظیمات یا تکرار سفارش نیست. فایل SQLite و نسخه‌های پشتیبان آن اطلاعات حساب دارند؛ دسترسی را محدود و با روش backup سازگار SQLite نسخه پشتیبان تهیه کنید. حذف تاریخچه یا کپی ناقص فایل در حال اجرا می‌تواند امکان بازیابی را از بین ببرد.

ایجاد فایل مسیر `kill_file` توقف را پایدار ثبت می‌کند، وزن هدف را صفر می‌کند و خرید جدید را می‌بندد. **فرایند را روشن نگه دارید** تا بتواند خروج محدود به سقف سفارش را تلاش و نتیجه را تطبیق کند. حذف فایل، توقف ثبت‌شده را بازنشانی نمی‌کند. حد زیان روزانه و حد افت نیز توقف پایدار ایجاد می‌کنند و پس از نیمه‌شب خودکار دوباره خرید نمی‌کنند.

قطع فرایند با Ctrl+C یا خاموشی ماشین موقعیت را خودکار نمی‌بندد. سفارش نامعلوم، کمبود موجودی آزاد، خطای API، spread زیاد، حداقل سفارش و محدودیت قیمت یا مقدار می‌توانند دارایی باقی بگذارند. برای `BLOCKED`، `STOPPED` یا `HALTED`، پیام خروجی و وضعیت واقعی حساب را بررسی و رفع ابهام را ثبت کنید؛ توقف نرم‌افزار را برابر با خروج کامل از بازار نگیرید.
