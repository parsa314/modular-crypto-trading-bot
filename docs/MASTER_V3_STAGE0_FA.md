وضعیت پس از اجرای موفق فرمان: `AWAITING_USER_REVIEW`.
معیارهای اقتصادی: `NOT_EVALUATED`. مجوز اجرا: `false`.
[گزارش شواهد آزمون](MASTER_V3_STAGE0_VALIDATION.md): ۵۲۹ تست موفق و یک تست PostgreSQL اجرا‌نشده.

پس از تحویل این مرحله، ادامه مراحل نیازمند دستور مالک است.

## آیا این پرامپت ارزش کار کردن دارد؟

برای کنترل پژوهش و مهندسی، بله: مراحل، کنترل ریسک و خروجی قابل پیگیری تعریف می‌کند.
ارزش اقتصادی ربات هنوز باید با داده واقعی و ارزیابی خارج از نمونه اندازه‌گیری شود.
پرامپت به‌تنهایی استراتژی، مدل آموزش‌دیده یا شواهد سودآوری نیست.
در این مرحله هیچ درخواست LLM، آموزش تازه، داده بازار، سیگنال معاملاتی یا سفارش ساخته نمی‌شود.

شرط «مدل پیچیده باید از مدل ساده بهتر باشد» شرط ارتقای اجراست؛ شکست آن نیز نتیجه معتبر پایان‌نامه است.
تغییر مکرر مدل روی همان test تا رسیدن به Sharpe مطلوب، اعتبار پژوهش را از بین می‌برد.
مدت ۳۰ روز Paper و ۶۰ روز Live Micro به مشاهده واقعی آینده نیاز دارد و با تست واحد اثبات نمی‌شود.
شیوه‌نامه پایان‌نامه باید از دانشگاه مشخص مالک دریافت شود؛ فونت، حاشیه، تعداد صفحه و آستانه همانندجویی
متن پرامپت، مقررات تأییدشده همه دانشگاه‌ها محسوب نمی‌شوند.

## ساختار مرحله ۰ و سازگاری با v0

```text
research_bot/
  research/                 # محل پژوهش‌های جدید؛ آزمایش‌های موجود حفظ شده‌اند
    __init__.py
    README.md
  execution/                # پایه اجرا با کتابخانه استاندارد و بدون import پژوهش
    __init__.py             # import تنبل API شبیه‌ساز قدیمی
    legacy.py               # همان execution.py قدیمی؛ importهای قبلی سازگارند
    config.py               # LiveConfig موجود + GovernanceConfig ثابت L0
    ledger.py               # همان دفتر ثبت بادوام قبلی، بدون تغییر رفتار
    logging.py              # قرارداد بسته رخدادهای JSON
    foundation.py           # فرمان مقداردهی مرحله ۰؛ هیچ اتصال صرافی ندارد
  live_runtime.py           # import سازگار LiveConfig؛ اجرای خصوصی فعلاً مسدود
  live_ledger.py            # import سازگار LiveLedger
  ensemble_*.py             # کد پژوهشی و fingerprintهای قبلی حفظ شده‌اند
configs/stage0.example.json
tests/test_foundation.py
artifacts/stage0/            # خروجی محلی، خارج از Git
  ledger.sqlite
  report.json
```

`LiveConfig` از کد موجود استخراج شده و `GovernanceConfig` آن را با composition گسترش می‌دهد.
فایل قدیمی `execution.py` به `execution/legacy.py` منتقل شده؛ API قبلی از بسته جدید به‌صورت تنبل عرضه می‌شود.
مقادیر `frozen` جلوی تغییر عادی از طریق assignment را می‌گیرند؛ محیط امن برای اجرای Python مخرب نیستند.
مدل‌ها در مسیر جدید اختیار ساخت یا تغییر L0 ندارند و هیچ مدل پژوهشی در پایه اجرا import نمی‌شود.
مهاجرت رابط مدل‌خوانی قدیمی و لایه‌های L1 تا L4 در مراحل مربوط انجام خواهد شد.
جداسازی کل برنامه قدیمی در مرحله ۰ تکمیل‌شده ادعا نمی‌شود.

حالت‌های قرارداد: `BACKTEST`, `PAPER`, `LIVE_MICRO`, `LIVE_FULL`.
نمونه تنظیمات فقط `BACKTEST` را مقداردهی می‌کند. صرافی، جفت‌ارز و سرمایه تا دریافت پاسخ مالک `null` هستند.
سقف زیان روزانه ۲٪ و افت ۱۰٪ از MASTER v3 گرفته شده‌اند؛ می‌توان سقف پایین‌تر تعیین کرد.
اعتبارسنجی LIVE نیازمند تنظیمات کامل است و سرمایه MICRO حداکثر ۵٪ سرمایه نهایی را می‌پذیرد.
تنظیمات کامل مجوز شروع معامله نیستند؛ فرمان foundation هر حالت دیگر را رد می‌کند.

ورودی عمومی `research_bot.live_runtime` حالت‌های خصوصی `live` و `testnet` را با کد خروج ۲ و
`BLOCKED_BY_MASTER_V3_GATE`، پیش از خواندن فایل، مدل یا کلید، رد می‌کند.
در این نسخه راه دور زدن یا پرچم override وجود ندارد. آداپتور و کنترل‌کننده قبلی برای آزمایش مهندسی حفظ شده‌اند؛
کد کتابخانه جایگزین گیت معتبر ارتقا نیست. پیاده‌سازی گیت ارتقا در مراحل بعد لازم است.

## اجرا و آزمون

از ریشه این شاخه، روی Linux و فایل‌سیستم محلی با SQLite و flock، با Python 3.11 یا جدیدتر:

```bash
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[dev,rl]'
python -m pip check
python -m research_bot.execution.foundation \
  --config configs/stage0.example.json \
  --ledger artifacts/stage0/ledger.sqlite \
  --report artifacts/stage0/report.json
python -m pytest -q tests/test_foundation.py tests/test_live_ledger.py tests/test_service_v1.py tests/test_v08_service.py
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 python -m pytest -q
```

فرمان foundation با `python -S` نیز اجرا می‌شود؛ برای این فرمان نصب ML یا CCXT لازم نیست.
extra مربوط به RL در فرمان نصب بالا برای اجرای کامل تست‌های موجود است و مرحله پژوهش جدیدی آغاز نمی‌کند.
تست یکپارچه PostgreSQL فقط با DB آزمون مناسب اجرا می‌شود؛ نبود آن باید صریحاً به‌عنوان skip گزارش شود.

گزارش شامل تنظیمات عمومی، SHA-256 تنظیمات و فایل‌های کد، نسخه Python و وضعیت هر ۱۵ مرحله است.
مرحله ۰ `AWAITING_USER_REVIEW` و مراحل ۱ تا ۱۴ `PENDING` می‌مانند.
اجرای مجدد با همان کد و تنظیمات دفتر را حفظ می‌کند. تغییر تنظیمات یا کد روی همان دفتر رد می‌شود؛
برای اجرای پژوهشی تازه، مسیر artifact تازه انتخاب و دفتر قبلی حفظ شود.
این دفتر مرحله ۰ را به‌عنوان دفتر حساب یا journal سفارش‌های واقعی استفاده نکنید.
گزارش JSON خروجی عمومی با دسترسی 0600 و جایگزینی اتمی نوشته می‌شود.

## سیاست اسرار و ثبت رخداد

- کلید در Git، چت، JSON تنظیمات، journal یا گزارش پژوهش قرار نگیرد؛ نمونه `.env.example` خالی است.
- فایل `.env` محلی خارج از Git و با `chmod 600 .env` نگهداری شود؛ foundation آن را بارگذاری نمی‌کند.
- لاگر مرحله ۰ فقط کد رخداد و فیلدهای محدود را ثبت می‌کند؛ متن خام exception، URL امضاشده، پیام آزاد و extra نامعتبر حذف می‌شوند.
- دفتر موجود کلیدهای credential را به‌صورت بازگشتی رد می‌کند؛ نباید پاسخ API خصوصی یا secret را داخل رشته عادی جاسازی کرد.
- پرچم‌های سرویس پژوهشی `false` می‌مانند؛ نتیجه علمی v0.50 و Kraken sealed حفظ می‌شوند.
